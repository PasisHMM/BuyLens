# Buy Lens Redesign Plan

> **Status:** decisions locked 2026-10-29; MVP decisions added the same day (§2.9–2.13, §5, §6c, §8, §9). Final MVP decisions applied: inclusive size boundaries, German stores, free sources only, Quick Fit sizes per category, **no market percentages**, **firsthand retail only**. Phase 0 and Phase 1 done. Next step: Phase 2 (execution plan in §9, awaiting approval).
> **Direction:** Buy Lens is a user-controlled, evidence-based clothing shopping analysis tool. It helps people decide; it never decides for them.

---

## 1. What changes

| From | To |
|---|---|
| BUY / CONSIDER / SKIP verdict with a headline | Plain **Fit**, **Price** and **Seller Reliability** findings |
| Waist / inseam / hips, bottoms only | Two profile modes (**Quick Fit**, **Personal Fit**) and category rules for jeans/pants, tops, dresses and outerwear |
| One weighted score | **Fit first:** MATCH → UNCERTAIN; MISMATCH hidden behind a note |
| Price vs "market average" with a percentage | Actual EUR retailer prices, shipping, total and budget fit. **No market percentages.** |
| Seller "risk" level | **Green / Yellow / Red** band from documented evidence, or "Not enough data" |
| A second copy of the rules in TypeScript (`mock/engine.ts`) | **The Python backend is the only place rules live.** The prototype shows sample results generated by the backend. |

What stays: extraction, fetching, the AI provider layer, sign-in and database access rules (RLS), the job queue, progress streaming, the cache and storage.

## 2. Locked product decisions

### 2.1 Critical measurements and tolerances

| Category | Critical (outside tolerance → MISMATCH) | Secondary (missing or off → UNCERTAIN only) | Tolerance |
|---|---|---|---|
| Jeans / pants | Waist, hips | Inseam | ±2 cm against a body chart, ±1 cm against a garment chart |
| Tops / T-shirts / sweaters | Chest / bust, shoulders | Waist | ±2 cm |
| Dresses | Bust, waist, hips | None | ±2 cm |
| Outerwear / coats | Chest, shoulders | None | ±3 cm (room for layers) |

Signed off by product; values may be tuned later from feedback. These values live in **one table** in `pipeline/measurements.py`.

> **Note:** Tops were corrected on 2026-10-29: chest/bust and shoulders are critical, waist is secondary.
> Shorts and skirts have no agreed rules yet, so they get no fit rules (fit result UNCERTAIN).

### 2.2 Profile modes

**Quick Fit (`QUICK_FIT`): XS / S / M / L / XL**
- For first-time users. The user picks a size system (**EU or US**; we ask first) and a size **per category, stored separately: at least Tops and Bottoms** (e.g. S in Tops, M in Bottoms).
- A check uses the size for the **product's fit category**. Top and bottom sizes are **never assumed to be the same**. If the user has no size for that category, fit is UNCERTAIN with the reason "Add your Bottoms size".
- **Size boundaries are inclusive:** a published range 66–70 cm includes 66 and 70. If two officially sourced ranges overlap, a boundary value may match both sizes. Overlaps are never invented.
- Sizes map to body ranges using this **source priority**: (1) the product's own size chart, (2) the brand's official size chart, (3) a documented general reference, used only as an approximate fallback. Every stored row records its source; see §6c.
- Quick Fit is always labelled approximate. It is never treated like exact body measurements.
- **Never returns MISMATCH.**
  - Returns **MATCH**, labelled "Approximate fit based on size M", when the store's chart covers that size.
  - Returns **UNCERTAIN** when the chart doesn't cover the size, or there's no chart.

**Personal Fit (exact measurements)**
- Measurements are **body** or **garment** (measured from a piece that already fits), with an optional note naming the garment.
- Garment measurements are compared only with **garment charts** published by the store. Body measurements are compared with the brand's **body charts**. If neither kind of chart exists, the measurement shows as **Missing data → UNCERTAIN**.
- Stretch allowance applies only when the fabric content is known.

**Switching** between Quick and Personal Fit keeps all checks, feedback, quick sizes and measurements. The mode is only a setting: switching never deletes the other mode's data. Each check records the mode it used.

### 2.3 Fit outcomes and ranking
- **MATCH:** every critical measurement is within tolerance.
- **UNCERTAIN:** a critical or secondary measurement is missing, the chart type is unknown, or the check ran in Quick Fit without chart coverage.
- **MISMATCH:** a critical measurement is outside tolerance and the data supports it (Personal Fit only).
- Results show MATCH options first, then UNCERTAIN in their own section. MISMATCH options are hidden behind **"3 options hidden due to critical measurement mismatches [View]"**.
- Within each group, options are sorted by: within budget → lowest total cost (EUR) → reliability band. No market average or percentage takes part.
- **No fit percentages or probabilities anywhere.**

### 2.4 Budget
- A single **maximum budget in EUR** (e.g. max €200) on the search screen. The profile holds the default.
- The total includes shipping when it is known or reliably estimated. Otherwise the app shows **"Shipping cost unverified"** and compares base prices.
- Only EUR offers can be checked against the budget (see §2.10).

### 2.5 Firsthand retail only (secondhand postponed)
- The MVP supports **new clothing from regular online retail stores**.
- **Postponed until after the MVP:**
  - the Secondhand checkbox;
  - Vinted, Kleinanzeigen and other marketplace integrations;
  - resale listing discovery;
  - secondhand-specific reliability logic.
- **Extensibility:** sellers stay a separate table and price stays per listing, so a marketplace source can be added later without redesign. No unused secondhand code or columns are built now.

### 2.5b Price (no market percentages)
- **Shown:** the actual retailer price in EUR, shipping (known, estimated from a verified store rule, or "Shipping cost unverified"), the total, and whether it fits the budget. Offers are compared by their EUR totals side by side.
- **Removed from the product:**
  - every market-percentage comparison ("x% cheaper / above market");
  - the market average it was based on;
  - any replacement percentage metric.

### 2.6 Seller reliability
- **Inputs:** platform rating and its count, review text, whether a return policy exists, and warning tags (delivery delays, item not as described, poor quality, fraud).
- **At least 5 reviews** are needed to show a band; otherwise **"Not enough data"**.
- **Bands:**
  - **Green:** reliable, positive feedback.
  - **Yellow:** mixed feedback, or minor delivery or description notes.
  - **Red:** high risk, with multiple quality or fraud complaints.
- Every input and its source is shown. **No percentages.**
- **How review text is used:** the AI only *tags* reviews. Each tag must quote text that exists word-for-word in a review, or it is dropped. The band itself comes from a fixed rubric that counts the tags, so the same evidence always gives the same band.

### 2.7 Prototype mode
- Sample results are generated by the Python engine and stored as fixture files that the Vercel prototype reads. No live Python host is needed.
- **Trade-off:** sample results no longer react to measurements a tester types in.

### 2.8 Production data
- `check_runs` has **0 rows** (confirmed 2026-10-29), so no stored results need migrating.

### 2.9 MVP product taxonomy (controlled vocabulary)

Eight product types. Each maps to one of the existing fit categories, or to none. Attributes describe the design. **An attribute never causes a MISMATCH**; only critical measurements do. A three-quarter sleeve is a design feature, not a fit problem.

| Product type | Fit category (rules from §2.1) | Attribute groups (max 3) and allowed values |
|---|---|---|
| Jeans | Bottoms | **fit:** skinny, slim, straight, relaxed, wide, bootcut, flare, tapered, barrel, mom, boyfriend · **rise:** low, mid, high · **length:** cropped, ankle, regular, long |
| Pants | Bottoms | **fit:** slim, straight, relaxed, wide, tapered, jogger · **rise:** low, mid, high · **length:** cropped, ankle, regular, long |
| Sweaters | Tops | **sleeve length:** sleeveless, short, three-quarter, long · **fit:** slim, regular, relaxed, oversized · **garment length:** cropped, regular, longline |
| Tops / cardigans | Tops | same groups as sweaters |
| Hoodies | Tops | **fit:** slim, regular, relaxed, oversized · **garment length:** cropped, regular, longline · **closure:** pullover, full zip, half zip |
| Skirts | **None → UNCERTAIN** | **length:** mini, knee, midi, maxi · **fit:** fitted, regular, relaxed · **shape:** A-line, pencil, straight, pleated, wrap |
| Shorts | **None → UNCERTAIN** | **length:** short, mid-thigh, knee · **fit:** slim, regular, relaxed · **waist rise:** low, mid, high |
| Hats | **None → UNCERTAIN** | **type:** beanie, cap, bucket, beret, fedora · **fit:** adjustable, fitted, one size · **material:** wool, cotton, acrylic, straw, synthetic |

- **One place:** a new `pipeline/taxonomy.py` holds the product types, the attribute vocabulary and the type → fit-category map. It replaces `CATEGORY_KEYWORDS` in `extract/attributes.py` and `_PRODUCT_CATEGORIES` in `measurements.py`.
- **Extraction:** keyword rules first. The AI fallback may only return values from the list (its JSON schema uses enums). Anything else is stored as "not stated", never as a free tag.
- **No new fit engine per type.** Types without approved rules return UNCERTAIN with the reason "No fit rules for this product type yet".
- **Dresses and outerwear** keep their rules in `measurements.py` but are not MVP product types. A product detected as one shows "Not supported in the MVP" (fit UNCERTAIN).
- **Extensible:** adding a type is one row in the map plus its vocabulary; it gets fit rules only after product approves them.

### 2.10 EU-first currency
- The MVP targets the EU. Prices are shown in **EUR, exactly as the retailer's EUR storefront offers them**.
- **No automatic currency conversion.**
- A listing in another currency keeps its **original price and currency**. It is labelled **"Not directly comparable to EUR offers"** and left out of the budget check and the EUR price comparison.
- An **unknown currency is "unknown"**, never assumed. Today the code silently assumes USD (§6c).
- Shipping and total-cost availability are always shown: known, estimated from a verified store rule, or **"Shipping cost unverified"**.

### 2.11 Homepage (first page)
One short form, no extra pages or buttons per feature:
1. **Product link**
2. **Quick Fit / Personal Fit** switch
3. **Category-specific size:**
   - Quick Fit shows two short rows of chips, **Tops** and **Bottoms**, each S / M / L (XS and XL behind "More sizes").
   - Personal Fit shows a one-line summary of the saved measurements with an "Edit" link.
4. **Maximum budget (€)**
5. **Analyze product**

- First-time users can analyze with Quick Fit straight away; the current forced redirect to `/preferences` goes.
- Existing styling and primitives are kept.
- **No secondhand checkbox. No payment or subscription UI.**

### 2.12 EU stores (priority) and technical access
**Priority:** Levi's Germany, H&M Germany, Zara Germany, Mango Germany, Uniqlo Germany.

A store is marked **supported** only after its product pages can be read with our honest bot identity (`BuyLensBot`, robots.txt respected). We never fake a browser identity or get around bot protection. Results on 2026-10-29 are in §6c: **no store passes yet**. Only Levi's official size chart page is readable.

### 2.13 Size reference sources: free and official only
- **Free sources only:** we buy no standard, API, dataset, subscription or service.
- **Allowed sources:**
  - the product's own chart;
  - the brand's official chart.
- **Each stored row keeps** its source URL, retrieval date and measurement basis (body or garment).
- **No reliable free source → UNCERTAIN**, never an invented value.
- **No generic fallback for now:** priority 3 (a general reference) stays empty until a free, official, legally usable one is found.

## 6c. Pre-Phase 2 verification (2026-10-29)

**Mutator: works now.** With Developer Mode on, Python creates file and folder symlinks. The run used a scratch copy of `measurements.py` with its 46 unit tests only (the full suite was not run): **17 sites, 10 killed, 7 survived, 0 uncovered; 16 s.** Every survivor is a boundary mutant (`<=` → `<`, `0` → `1`), meaning no test checks a value exactly on a limit:
- `is_plausible` at exactly the low and high limit
- `SizeReference.covers` at exactly `min_cm` and `max_cm`
- a tolerance of exactly 0
- `min_cm == max_cm`

These tests are added as the first unit of Phase 2. **Decided:** limits are inclusive (§2.2), which pins the current `<=` behaviour.

**Size reference sources: feasibility.**

| Priority | Source | Feasibility | Notes |
|---|---|---|---|
| 1 | Product's own chart | **Works today** | `extract/sizechart.py` already reads it at check time, and the chart type (body or garment) is recorded |
| 2 | Brand chart: Levi's (levi.com/DE) | **Readable** | Body measurements in cm, plain HTML. Women's: jean sizes 24–34 with waist and hip, alpha XXS–XXL mapped to jean sizes, inseam by height. Example row: jean 26 → waist 69 cm, hip 91.5 cm. |
| 2 | Brand chart: H&M | **Blocked** for automated reads (HTTP 403) | Would need manual entry from a browser |
| 2 | Brand chart: Mango | **Rate-limited** (HTTP 429) | Manual entry only |
| 2 | Brand charts: Zara, Uniqlo | **Per product and script-rendered** | Uniqlo says its garments vary by about 1 cm and points to each product's chart. Better handled as priority 1. |
| 3 | Paid standards (e.g. EN 13402-3) | **Excluded** | Free sources only (§2.13) |
| 3 | Free aggregator sites (size.ly, size-charts.com, sizechartbase) | **Not acceptable** as a source | Copies of brand charts with no stated origin, and they disagree with each other |

**Recommendation:**
- **Rely on priority 1** (product charts, already working) for both modes.
- **Brand charts** come only from the brand's own free page. Each row stores the source URL, retrieval date and basis. **Levi's DE is the only one readable today.** H&M, Zara, Mango and Uniqlo refuse or time out for automated reads.
- If the team copies those charts by hand from a browser, check each brand's terms of use first. Brand chart values are factual measurements, but copying whole tables may still be restricted.
- **No generic fallback.** Without a product or brand chart, Quick Fit returns UNCERTAIN.
- **Schema:** this needs extra `size_references` columns (brand, source URL, retrieved date, basis, source kind) and size labels beyond XS–XL (EU numbers, W/L). Planned for Phase 3.

**EU store access (2026-10-29).** Probed with our real fetcher identity (`BuyLensBot/0.2`), respecting robots.txt, one request per page, with no browser disguise:

| Store | robots.txt | Product or listing page | Size chart page | Supported? |
|---|---|---|---|---|
| Levi's DE | 200, allows `/DE/...` | **403** (listing and home) | **200** (`/DE/en/info/sizechart`) | **No** for products; yes as a brand-chart source |
| H&M DE | **403** (our fetcher reads this as "disallow all") | 403 | 403 | **No** |
| Zara DE | **403** | 403 | 403 | **No** |
| Mango DE | **429** (rate-limited) | 429 / 403 | — | **No** |
| Uniqlo DE | timeout | timeout | timeout | **No** (retest later) |

**Implication (risk R1):** the live product needs to read the product page the user pastes, and **none of the five priority stores allows that today**. Allowed options, in order:
1. **The user's own browser reads the page.** A small browser extension or bookmarklet sends the product page the user is already viewing. No bot is involved, and there are no paid services.
2. **Manual fallback:** the user pastes the size chart or price.
3. **Official partner feeds:** product feeds through free affiliate or partner programmes, only if the terms allow it.

We will not fake a browser identity, use a headless browser to get past blocks, or route requests through proxies. The prototype is unaffected, because it runs on fixtures. This is a product decision; it is not part of Phase 2.
