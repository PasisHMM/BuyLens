# Buy Lens Redesign Plan

> **Status:** decisions locked 2026-10-29. Phase 0 and Phase 1 done. Next step: Phase 2 (awaiting review).
> **Direction:** Buy Lens is a user-controlled, evidence-based clothing shopping analysis tool. It helps people decide; it never decides for them.

---

## 1. What changes

| From | To |
|---|---|
| BUY / CONSIDER / SKIP verdict with a headline | Plain **Fit**, **Price** and **Seller Reliability** findings |
| Waist / inseam / hips, bottoms only | Two profile modes (**Quick Fit**, **Personal Fit**) and category rules for jeans/pants, tops, dresses and outerwear |
| One weighted score | **Fit first:** MATCH → UNCERTAIN; MISMATCH hidden behind a note |
| Seller "risk" level | **Green / Yellow / Red** band from documented evidence, or "Not enough data" |
| A second copy of the rules in TypeScript (`mock/engine.ts`) | **The Python backend is the only place rules live.** The prototype shows sample results generated by the backend. |

What stays: extraction, fetching, the AI provider layer, sign-in and database access rules (RLS), the job queue, progress streaming, the cache and storage.

## 2. Locked product decisions

### 2.1 Critical measurements and tolerances

| Category | Critical (outside tolerance → MISMATCH) | Secondary (missing or off → UNCERTAIN only) | Tolerance |
|---|---|---|---|
| Jeans / pants | Waist, hips | Inseam | ±2 cm against a body chart, ±1 cm against a garment chart |
| Tops / T-shirts / sweaters | Chest / bust, shoulders | Waist | ±2 cm |
| Dresses | Bust, waist, hips | None | ±2 cm |
| Outerwear / coats | Chest, shoulders | None | ±3 cm (room for layers) |

Signed off by product; values may be tuned later from feedback. These values live in **one table** in `pipeline/measurements.py`.

> **Note:** Tops were corrected on 2026-10-29: chest/bust and shoulders are critical, waist is secondary.
> Shorts and skirts have no agreed rules yet, so they get no fit rules (fit result UNCERTAIN).

### 2.2 Profile modes

**Quick Fit (`QUICK_FIT`): XS / S / M / L / XL**
- For first-time users. The user picks a size system (**EU or US**; we ask first) and a size per category.
- Sizes map to approximate body ranges from standard conversion tables. Each table row records its source.
- **Never returns MISMATCH.**
  - Returns **MATCH**, labelled "Approximate fit based on size M", when the store's chart covers that size.
  - Returns **UNCERTAIN** when the chart doesn't cover the size, or there's no chart.

**Personal Fit (exact measurements)**
- Measurements are **body** or **garment** (measured from a piece that already fits), with an optional note naming the garment.
- Garment measurements are compared only with **garment charts** published by the store. Body measurements are compared with the brand's **body charts**. If neither kind of chart exists, the measurement shows as **Missing data → UNCERTAIN**.
- Stretch allowance applies only when the fabric content is known.

**Switching** from Quick to Personal Fit keeps all checks and feedback. Each check records the mode it used.

### 2.3 Fit outcomes and ranking
- **MATCH:** every critical measurement is within tolerance.
- **UNCERTAIN:** a critical or secondary measurement is missing, the chart type is unknown, or the check ran in Quick Fit without chart coverage.
- **MISMATCH:** a critical measurement is outside tolerance and the data supports it (Personal Fit only).
- Results show MATCH options first, then UNCERTAIN in their own section. MISMATCH options are hidden behind **"3 options hidden due to critical measurement mismatches [View]"**.
- Within each group, options are sorted by: within budget → lowest total cost → reliability band.
- **No fit percentages or probabilities anywhere.**

### 2.4 Budget
- A single **maximum budget slider** (e.g. max €200) on the search screen. The profile holds the default.
- The total includes shipping when it is known or reliably estimated. Otherwise the app shows **"Shipping cost unverified"** and compares base prices.

### 2.5 Secondhand
- A **Secondhand** checkbox on the search screen.
- **MVP:** only links the user pastes (e.g. a Vinted listing). We read that single page. **No automated marketplace search or scraping.**

### 2.6 Seller reliability
- **Inputs:** platform rating and its count, review text, whether a return policy exists, and warning tags (delivery delays, item not as described, poor quality, fraud).
- **At least 5 reviews** are needed to show a band; otherwise **"Not enough data"**.
- **Bands:**
  - **Green:** reliable, positive feedback.
  - **Yellow:** mixed feedback, or minor delivery or description notes.
  - **Red:** high risk, with multiple quality or fraud complaints.
- Every input and its source is shown. **No percentages.**
- **How review text is used:** the AI only *tags* reviews. Each tag must quote text that exists word-for-word in a review, or it is dropped. The band itself comes from a fixed rubric that counts the tags, so the same evidence always gives the same band.

### 2.7 Prototype mode
- Sample results are generated by the Python engine and stored as fixture files that the Vercel prototype reads. No live Python host is needed.
- **Trade-off:** sample results no longer react to measurements a tester types in.

### 2.8 Production data
- `check_runs` has **0 rows** (confirmed 2026-10-29), so no stored results need migrating.

## 3. Target architecture

```
backend (Python): the only place rules live
  1 Extraction     KEEP     fetch · JSON-LD · Shopify · size chart · AI fallback
  2 Sourcing       MODIFY   retail search + user-pasted secondhand links
  3 Measurements   NEW      catalog · categories · critical / secondary · tolerances · size references
  4 Fit analysis   REPLACE  MATCH / UNCERTAIN / MISMATCH + reasons (pure, deterministic)
  5 Price          MODIFY   total cost incl. shipping · budget flag · "shipping unverified"
  6 Reliability    REPLACE  evidence → rubric → Green / Yellow / Red / Not enough data
  7 Ranking        NEW      fit group → budget → total cost → band; mismatches counted, hidden
  8 AI evidence    NEW      review tags + verified quotes (no recommendation)
  9 Feedback       MODIFY   saved on the server; fit_memory adjustment shown to the user
                      │ JSON contract
web (TypeScript): display only. Prototype reads backend-generated fixtures.
```

## 4. Data model and API

**Migration A (additive):**

| Table | Change |
|---|---|
| `profiles` | Add `fit_mode` (`quick_fit` / `personal_fit`) and `size_system` (`eu` / `us`) ✅ Phase 1; `budget_max_cents`, `budget_currency`, `include_secondhand` in Phase 6 |
| `quick_sizes` (new) | `(user_id, category, size_label)` |
| `size_references` (new, seeded) | `(system, category, size_label, dimension, min_cm, max_cm, source)` |
| `fit_measurements` | Add `basis` (`body` / `garment`) and `garment_note`; dimension must be in the catalog |
| `sellers` | Add `kind` (`retail` / `marketplace`) and `platform` |
| `listings` | Add `condition` and `marketplace_seller` (JSON: rating, count, account age) |
| `check_runs` | Add `analysis_version`, `fit_mode_used`, `budget_max_cents`, `include_secondhand`, `summary` (JSON) |
| `analysis_results` (new) | Per option: `fit_outcome`, `fit_reasons`, `price`, `reliability`, `sort_keys`, `evidence` |

**Migration B (after nothing reads the old columns):** drop `verdict`, `headline`, `explanation`, `why_not`, `check_options.score`, the enums `verdict` and `skip_reason`, and the table `decision_memory`. Keep `fit_memory`.

**API:**

| Endpoint | Change |
|---|---|
| `GET /v1/measurements` (new) | Catalog, categories and size labels |
| `PUT /v1/profile` | Mode, size system, quick sizes, measurements with basis, budget default, secondhand default; old bodies still accepted |
| `POST /v1/checks` | Body `{url, budget_max_cents?, include_secondhand?}`, plus an `Idempotency-Key` header |
| `GET /v1/checks/{id}` | Returns `matches[]`, `uncertain[]`, `hidden_mismatches{count, reasons}`, `fit_mode_used`; **no `verdict`** |
| `POST /v1/checks/{id}/feedback` (new) | Saves feedback on the server |

**Prototype browser data:** stored under new `bl:v2:*` keys and validated when read. Old `bl:*` profiles are converted to Personal Fit body measurements.

## 5. Roadmap

Every unit follows the same rules:
- Write a failing test first and watch it fail for the expected reason, then make the smallest change that passes it.
- Gates: **crapper** (changed functions CRAP < 10), **dryer** (no duplicates ≥ 0.8), **mutator** on changed files, CI green.
- One small commit per unit. Push only with approval.

| Phase | Scope | Tests to write first | Done when |
|---|---|---|---|
| **0 Stabilise** ✅ | Worker allow-list race; Vitest + first web tests; CRAP baseline with coverage | Concurrent refresh keeps hosts allowed; formatting; mock-client storage | Done: see §6 |
| **1 Measurement model** ✅ | `pipeline/measurements.py` (table in §2.1, size references with sources), fit-mode / outcome / basis enums, Migration A (profile part), `docs/glossary.md` | Critical and secondary sets per category; tolerance by chart basis; unknown dimension/category rejected where data enters; every size reference has a source | Only one definition of the catalog exists |
| **2 Profiles** | Quick Fit and Personal Fit API and form, `GET /v1/measurements`; the web form reads the catalog (removes the duplicated `PLAUSIBLE_CM`) | Quick Fit valid with sizes only; Personal Fit requires critical measurements; switching keeps checks and feedback; old bodies accepted | A first-time user can run a check with "M" only |
| **3 Fit analysis v2** | `fitting.py` replaced (size choice and length variants reused), `sizechart.py` aliases (pin current behaviour, then split `parse_table`) | Jeans MATCH / UNCERTAIN (hips missing) / MISMATCH (waist); body vs garment tolerance; Quick Fit never MISMATCH; stretch only with fabric content; inseam missing → UNCERTAIN, never MISMATCH | Deterministic; no percentages |
| **4 Remove verdicts** | `ranking.py`; delete `rules.decide` and `narrate.py`; new results contract; results screen (match / uncertain / hidden note); delete `mock/engine.ts`; fixtures from Python; `live.ts` duplicate; check data where it enters the web app; idempotency key | MATCH ranks above a cheaper UNCERTAIN option; mismatches counted and hidden; no `verdict` key; malformed responses rejected; double submit makes one check | No BUY / CONSIDER / SKIP in active code; dryer clean |
| **5 Reliability + evidence** | `reliability.py`, `evidence_summary.py` | Fewer than 5 reviews → Not enough data; fixed tags → expected band; tag with an unverifiable quote dropped; no percentages | Every input and source is visible |
| **6 Budget + secondhand** | Slider and checkbox; total including shipping; "Shipping cost unverified"; condition parsing; pasted Vinted link (after access check) | Over-budget flag; secondhand excluded unless ticked; unknown shipping compares base price with a warning | Retail and secondhand options in one list |
| **7 Feedback on the server** | Feedback endpoint, `fit_memory` adjustment shown to the user | Saving twice changes nothing; adjustment capped; feedback survives a mode switch | Feedback is no longer browser-only |
| **8 Clean-up** | Migration B, docs, methodology page, final quality report | Migration and RLS tests | No verdict code or columns left |

**Estimate:** about 6–8 weeks for one developer. The smallest usable version (Phases 1–4: jeans, the pasted link, budget flag) takes about 4 weeks.

## 7. Open items

1. **Mutator on Windows:** turn on Windows Developer Mode (Settings → System → For developers) or run mutation tests on Linux.
2. **Vinted access:** confirm their terms allow reading a single user-submitted page, and check whether pages can be fetched without a browser. Needed before Phase 6.
3. **Currency:** the budget is in € while current stores price in USD. Do we convert currencies, or only compare options in the same currency?
4. **Size reference values:** the official EN 13402-3 tables are paywalled (CEN/BSI/DIN), and the free tables found are secondary or brand-specific. Choose the source: buy the standard, or approve specific brand charts. `size_references` stays empty until then, so Quick Fit can only return UNCERTAIN.
5. **Quick sizes for bottoms:** jeans are usually sized W/L or EU numbers, not XS–XL. Should Quick Fit accept those for bottoms?
6. **Body and garment value for the same measurement:** `fit_measurements` keeps the primary key (user_id, dimension), so one value per measurement for now. Allowing both changes the key in Phase 2.
7. **Database name for the fit outcome:** `fit_outcome` already names the feedback enum (too tight / fits well / too loose). The analysis result will get a different database type name in Phase 3/4; see docs/glossary.md.
8. **Shorts and skirts:** add rules, or keep them unsupported?
